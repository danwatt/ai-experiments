Design system · from danwatt/geo-tagger

GeoTagger

A photo library, put in its place. Near-black surfaces so the only saturated colour on screen is the photograph, one blue accent, status colours that always carry a word, and emoji for icons.

Components

Actions

Button

Default, active, primary, danger, icon and disabled
Usage guidelines

The app's one button, in the five variants style.css defines: default, active, primary, danger and icon-only.

Every clickable control in GeoTagger is this button. It is deliberately small — 12px label, 4px/10px padding — because toolbars carry eight or ten of them at once and the photographs need the room.

When to use

  • Default for any ordinary action. control fill, control-border, ink label.
  • .active for a toggle that is currently on, or the current page in the nav. accent-fill + accent border + accent-text label.
  • .primary for the one action a panel exists to perform — "Apply this guess". Same fill as .active, hovering to accent-fill-deep. Never put two primaries in one group.
  • .danger for a destructive or stop action. Border and label only; the fill stays neutral until hover, so a Stop button sitting beside a running job does not shout.
  • .icon-btn for a single-glyph action (✓ ✕ 🚫) in a dense row. Always give it a title.

<a class="button"> and <button class="button"> are styled identically, so a link that navigates and a button that acts look the same — pick by what the element actually does.

What the consumer provides

The label text (a verb phrase, sentence case), an optional leading emoji separated by a space, and disabled where it applies. For a long-running job, rewrite the label in place as the client loop progresses ("Detect faces" → "Detecting… 3,410 left") rather than adding a spinner.

Don't

  • Don't invent a size scale. The only variation is .icon-btn, and .face-group-header .button at 11px inside a group header.
  • Don't use .primary for navigation.
  • Don't set a background on .danger at rest — the hover danger-surface is the whole signal.

TouchActionBar

The Quick Tag answer bar
Usage guidelines

The fixed bottom bar of thumb-sized answers on the phone pages (Quick Tag, Quick Geocode).

Quick Tag asks one question at a time — "is this Marion?" — and this bar is the whole answer surface. The buttons are 16px tall padding, radius-12, touch-action weight 700, and they fill the width evenly so a thumb never has to aim.

When to use

Only on a single-question touch flow. A desktop pane uses Button instead.

Three roles, left to right:

  • .skip — a fixed 80px escape hatch, lighter weight, ink-secondary. Always present, never primary.
  • .act — neutral alternatives (field fill).
  • .act.primary — the confirming answer, in success-action with on-success-action. Exactly one per bar.
  • .act.danger — the destructive answer ("Not a face"), in danger-action.

What the consumer provides

The labels, the disabled state while a request is in flight, and the safe-area padding — the bar already adds env(safe-area-inset-bottom) in the app, which the preview omits.

Don't

  • Don't exceed four buttons; a thumb loses the row.
  • Don't put the destructive and the confirming button adjacent — the app keeps a neutral between them.
  • Don't shrink the 16px vertical padding to fit another control.

Data

Chip

Filter chips, family chips, list counts and summary badges
Usage guidelines

The small lozenges that carry a selected filter, a group name, or a count.

Four related shapes, all rounded past radius-8 so they read as tokens rather than buttons:

  • .person-chip — a person added to a search filter: accent-fill, accent border, on-accent text, 12px radius, with a ✕ that removes it. This is the only chip a person dismisses.
  • .family-chip — a family on People Manager: a muted blue #2a3a4e on #4a6a8e, radius-pill, with the name (click to rename in place) and a .family-count bubble.
  • .person-count — the faces-per-person bubble in a list row: control fill, ink-muted, flush right, going accent-fill-deep when its row is active.
  • .count-badge — a figure in a summary row, with .count-geotagged (success), .count-not-geotagged (danger) and .count-total (ink-muted, 600) saying which figure it is.

When to use

A chip means *this is currently applied* or *this is how many*. If clicking it would perform an action rather than remove a filter, it is a Button.

Because success and danger sit close in lightness, a count chip always carries its own word — "geotagged", "not geotagged" — so the pair never depends on hue.

What the consumer provides

The text, the removal handler on .person-chip, and the rename handler on .family-chip. Chips wrap in a flex row at a 4–8px gap; the container hides itself when empty (#person-chips:empty { display: none }).

Don't

  • Don't put a chip in a toolbar as a control — chips are output.
  • Don't colour a count chip without its label word.
  • Don't let a chip's text truncate silently; cap the name at 160px with an ellipsis and keep the count visible.

CoverageBar

Four-way library split, plus coverage by month
Usage guidelines

The segmented bar that splits the library four ways at once, with a legend whose swatches are the segments themselves.

A 14px flex track on field, its children sized by percentage: .cov-full (success, every face named), .cov-partial (warn, some named), .cov-none (danger, none named), .cov-noface (control-hover, no faces found). The legend reuses the same class on a 10px .sw square, so a segment and its key can never drift apart.

When to use

For a whole-library breakdown into mutually exclusive states, on a .card-full tile. The month-bar variant does the same job over time: one 4px column per month, stacking bar-tagged (success) under bar-untagged (control-hover), scrolling horizontally with a year label floated above each January.

success, warn and danger sit close in lightness, so the legend is not optional — it is what makes the bar readable. Every segment's meaning is spelled out in words beside its swatch.

What the consumer provides

The four percentages (they must total 100), the legend labels, and the counts. A segment at 0% should be omitted rather than rendered at hairline width.

Don't

  • Don't add a fifth segment; four is already at the limit of what 14px can distinguish.
  • Don't ship it without the legend.
  • Don't reuse these colours for anything that is not this four-way split.

MetaTable

Detail metadata, an editable record table, and key caps
Usage guidelines

The two-column key/value table in a detail pane, and its wider editable sibling on People Manager.

Detail table (.gt-meta-table, #detail-meta in the app): full width, collapsed borders, 12px, a rule under each row, keys in ink-dim at a fixed 40% column, values in ink and top-aligned so a long path wraps under itself rather than pushing the key around.

Data table (.gt-data-table, #persons-table): a real table of rows with 600-weight ink-dim headers over a hairline, rows on a #2a2a2a rule that light to #282828 on hover, and explicit column widths so the name column does not collapse when a family name is long.

When to use

The detail table for the metadata of one selected thing — filename, timestamp, camera, coordinates, place, people. The data table for a list of records a person edits in place.

Inline editing uses .edit-input: a transparent field that looks like text until hovered (a field-border outline appears) and focused (accent border, canvas fill). There is no edit mode and no save button; a blur writes.

.gt-kbd renders a key cap in a shortcuts table — control fill, control-border, inheriting the UI font so it matches its row.

What the consumer provides

The rows. Format values before they arrive: coordinates to a fixed precision, timestamps in the library's own timezone, sizes already humanised.

Don't

  • Don't put a key in ink-faint or below — at 12px it stops being readable.
  • Don't give the detail table a header row; the keys are the header.
  • Don't use a data table where a list of ThumbCells would do.

ProgressBar

Two jobs mid-run, with a stoppable batch loop
Usage guidelines

The 10px track that shows how far through the library a long job has got.

field track, 5px radius, an accent fill whose width animates over 0.3s, and an 11px ink-muted label beneath giving the real numbers. The fill is the app's only use of solid accent as a large area.

When to use

Inside a Card, for a ratio over the whole library: photos geotagged, photos face-scanned. Always pair it with .progress-label — the bar gives the shape, the label gives the count, and a person managing 48,000 photos needs the count.

Long server work is driven as a client loop (POST a batch, read remaining, repeat), so update the width and label on each round-trip. The button that started the job rewrites its own label alongside; there is no spinner and no modal.

What the consumer provides

The percentage for the width and the formatted label ("12,880 of 48,201 · 27%"). Never show the bar without a number, and never show a percentage without its absolute counts.

Don't

  • Don't use it for an indeterminate wait — there is no indeterminate variant, by design.
  • Don't colour the fill by status; that is CoverageBar's job.
  • Don't animate anything but the width.

Forms

Select

Default, width-capped, and page-scoping
Usage guidelines

The native dropdown, styled to match TextField and left native everywhere else.

field fill, field-border, radius-4, 4px/6px padding, ink-strong. The app never replaces it with a custom listbox — a native select gets keyboard behaviour, type-ahead and the OS picker on touch for free, and this is an offline single-user tool with no reason to reinvent it.

When to use

For a closed set of options: camera, time window, family filter, an imprecise-drop radius. Cap the width where the option text can run long (max-width: 240px on the focus and unlabeled pickers) so one long place name cannot stretch a toolbar.

.focus-active marks a select whose choice is currently scoping the whole page — accent border over a #24374d fill. Use it only for a filter with page-wide reach, so it is obvious why the results look short.

What the consumer provides

Options, the current value, and the change handler. Where a select scopes the page, also provide the note beside it saying what is in scope.

Don't

  • Don't build a custom dropdown to get a swatch or an icon into an option.
  • Don't use .focus-active for every filter — it stops meaning anything.
  • Don't leave a page-scoping select unlabelled.

SettingRow

A settings group: number, checkbox, select, and a rejected value
Usage guidelines

One tunable knob on the Settings page: its name, the control, the sentence explaining it, and the env-var default it overrides.

Rows stack inside a .settings-group — a Card by another name — separated by a rule bottom border that the last row drops. The name is label weight 500 in ink; the help is 11px ink-soft at 1.4 line-height; the control sits in its own flex row.

When to use

For every entry in the backend's SETTINGS_SPEC. These settings are persisted to the database and applied live, so the row must say so rather than implying a restart.

Its parts:

  • .setting-label — the name, with a small reset Button pushed to the right edge.
  • .setting-help — one or two sentences, ending with the env-var default in the form the backend names it (GEOTAGGER_FACE_MATCH_THRESHOLD, default 0.42).
  • .setting-control — a number input (110px), a checkbox (18px, accent-color: accent), or a select.
  • .setting-saved-flash — an 11px success "Saved" that fades in on write and out again. It is the only save feedback; there is no save button.
  • .setting-error — 11px danger-text under the control when a value is rejected.

What the consumer provides

The spec entry: name, help sentence, control type, bounds, and the env-var default to quote. Writes go out per change; nothing is batched.

Don't

  • Don't add a Save button — it would contradict "changes apply immediately".
  • Don't hide the env-var default; it is how a person reconciles the UI with their shell.
  • Don't let the help text exceed two sentences.

ThumbCell

Selection, badges, suggestion chips and dimmed states
Usage guidelines

The square image tile — a photo thumbnail or a face crop — and the full vocabulary of badges, chips and dimming layered over it.

One square (aspect-ratio: 1, object-fit: cover), radius-3, a 2px transparent border that becomes accent when selected, and media-well behind the image so a slow tile is a dark hole rather than a flash of pane. It is the densest thing in the app and the most heavily overloaded: every piece of state a photo or a face can be in shows here.

When to use

In any grid of media. The grid is always repeat(auto-fill, minmax(var(--face-size), 1fr)) with a 4px gap, so photo grids, face grids and cluster strips all agree on tile size.

Selection and identity

  • .selected — 2px accent border.
  • .ambiguous — a 2px inset warn-ring: the matcher could not choose between two people.

Badges, pinned into corners

  • .tagged → 📍 bottom-right; .geo-ignored → 🚫 top-left plus opacity-geo-ignored on the image. Both get text-shadow: 0 0 3px #000 to survive a light photo.
  • .face-score — a 9px match score, top-right, on its own dark pad.
  • .cam-strip — a 4px band across the top in the camera's legend colour.

Captions along the bottom edge, all on a scrim so they hold over any image:

  • .thumb-name — the filename, caption-scrim, revealed on hover only.
  • .face-label — a settled name, always visible.
  • .face-suggest — a clickable proposal on rgba(42,74,110,.85): a ✓ in green, the name, and a .sug-reject ✕ in danger-quiet that brightens to danger-hot. Accept and reject are always both present.

The src, the state classes, and a click handler on the cell (the img is pointer-events: none so a click always lands on the cell). Every chip needs its own handler; they stop propagation.

  • Don't show a suggestion without its reject affordance.
  • Don't put a caption on a tile without caption-scrim behind it.

PersonPicker

Desktop dialog, its empty state, and the touch bottom sheet
Usage guidelines

The "assign this face to…" typeahead — a small centred dialog on desktop, a bottom sheet on touch.

overlay panel, accent border, radius-8, shadow-float, 260px wide and 60vh tall, opened 12vh down the viewport at z-picker over a scrim backdrop. A search field, then a scrolling list of rows, each with the person's name left and a pp-count of their faces right.

When to use

Anywhere a face gets a name: the People toolbar, the People detail pane, the quick-action popup on a tile. It is deliberately the same dialog in all three, so the interaction is learned once.

Confirmation and failure, over the Quick Tag action bar
Usage guidelines

The transient lozenge that confirms a write, or reports that one failed.

GroupSection

Two consecutive day groups on cycling tints
Usage guidelines

The tinted wrapper that fences one day, event or cluster of tiles off from its neighbours.

A tint-border outline, radius-5, a FaceGroupHeader flush at the top, and a tile grid beneath it on one of six cycling tints (group-tint-0 … group-tint-5). The tints are 9% alpha — just enough that two adjacent days read as two things without a hard rule between them.

When to use

Wherever a flat grid would run two unrelated groups together: day and event groups in the photo grid, suggested-person runs in the unlabeled face queue, clusters on Discover, near-duplicate runs on Representatives.

What the consumer provides

The header (title, meta, buttons) and the tiles. In a queue where the first tile of each run must start a fresh row, tag it .row-break — CSS grid auto-placement cannot backfill, so the previous row's tail stays empty and becomes the visual break.

Don't

  • Don't raise the tint opacity; at 9% it sits under a photograph without colouring it.
  • Don't use the tint to encode state. Two green groups can be tinted differently and still both mean "labeled".
  • Don't nest sections.
